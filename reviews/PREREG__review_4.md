## Part 4 — Findings

### MAJOR

**M1. §6.0 is one global sequence over two devices; it cannot be executed as written while G is unavailable, and it contradicts `DECISIONS.md` 2026-10-12 ("GPU arms wait for NVIDIA Inception credits; all local work first").**
Step 1 includes the §5 one-fit check "on G"; step 2 is "timing pilots on every unit"; step 6 deposits `PROJECTIONS.md` "with the step-5 outcome"; step 7 is "Runs". Read literally, no library, logreg, H2 construction or H5 run on C may start until the G pilots exist, i.e. until the credits arrive. A doer today either waits (violating the DECISIONS row) or starts C work out of order (violating §6.0). The H2-A rebuild and the H2-B masks, both on C and prerequisites for execution positions 1 and 4, appear nowhere in the order. Nothing in the C pipeline depends on a G decision: the §6.4 PCA trigger affects only TabPFN arms, the library cap (§6.5) needs only C pilots, and the budgets are already per device.
*Fix.* State that §6.0 is applied **per device queue**, each with its own `PROJECTIONS.md` section deposited before that queue's first non-pilot run: **C queue** — T03 (§6.8) → H2-A construction and H2-B masks for all four sets (with the overlap checks of §H2) → C pilots (library, logreg, H5) → §6.5 caps → §6.7 caps/budgets for C → C runs in §6.7 order (positions 1, 3, 4, 6-logreg-free parts, 7, 8-logreg/library); **G queue** — `DEVICE_LOG.md` → §5 → G pilots → §6.4 PCA trigger → §6.7 caps/budgets for G → G runs in §6.7 order. Name the two cross-dependencies explicitly: G runs on rebuilt rows wait for the H2-A files; the §1.9 MPS arms and §6.9 belong to the G queue only if the fallback switch is thrown, otherwise to the C queue's tail. Add that the execution order of §6.7 is applied *within* each queue.

### MINOR

**m1. H2-B's S_f is defined on raw source indices, but the CSV identifies members by vector id; on Medical the index-defined purge leaves vector-identical instances in training.**
`verify_knn_bags.py` writes `member_rows` as the lowest index among byte-identical source rows ("vector ids") and `centre_row` as the bag index. Medical has 11 source rows whose vector duplicates a lower-indexed row, Corel5K 2 (Emotions and Yeast 0). Recomputed per canonical fold: after the purge as written, **Medical keeps 9, 9, 10, 7, 8, 9, 7, 6, 8, 9 surviving training bags that still contain an instance vector present in a test bag; Corel5K 2, 1, 1, 1, 0, 1, 1, 1, 2, 1**; all of them are training *centres* whose vector equals a lower-indexed id that occurs in a test bag. The effect on AP is negligible (≈ 1 % of surviving Medical bags, one row each), but the leak-purge arm is then not leakage-free by its own definition, and a doer following the text would not notice, because the zero-overlap check is demanded only for H2-A.
*Fix (three clauses).* (i) "Source indices in H2 are vector ids: a source row byte-identical to a lower-indexed source row is identified with that row, for centres as for members (the map `verify_knn_bags.py` already computes)." (ii) Add to the overlap quantification: "for the leak-purge arm, the share of test instance vectors present in surviving training bags must be exactly 0 in every fold; a non-zero value stops the run as a construction bug" (as H2-A already says). (iii) Define "the centre row" as an instance position for the purge and the control: "the first instance of bag i that equals source row i; any further identical instance in the bag is a non-centre row." Report the duplicate counts (11 / 2) in the descriptive table. The centre-deletion rates in the table change by at most 1 % on Medical and should be regenerated by the same script after (i).

**m2. §1.9's gates descope units without a user decision.** "each arm only where its own §6.3 projection on MPS is ≤ 72 MPS-hours" and "nested library only where ≤ 300 process-hours" are self-executing drops, whereas §6.7 and the `DECISIONS.md` 2026-10-13 row say a unit is dropped only by a user decision. Both readings are defensible; the document must pick one. *Fix.* Either (a) state that §1.9's gates are pre-registered **inclusion criteria** for an EXPLORATORY analysis, exempt from the stop rule, with arms above the gate reported "not run (pre-registered §1.9 gate; projection [h])"; or (b) route them through the stop rule like every other unit. (a) is the cheaper and matches the intent of round 3 M4.

**m3. N = 8 concurrent JVMs at `-Xmx8g` on a 24 GiB machine, plus MPS unified memory.** `sysctl hw.memsize` = 24 GiB. Eight heaps *allowed* to reach 8 GiB each is 64 GiB; `run_kdis_baselines.py` already passes `-Xmx8g`. On the small sets the heaps stay far below the cap, but on VOC2012 (10 386 training bags: an 863 MB double distance matrix per run plus Weka's instance overhead) and Corel5K-R eight concurrent runs can swap, which inflates sys CPU time and breaks "no more and no fewer" when the doer is forced to lower N. §1.9's TabPFN-on-MPS process also draws from the same 24 GiB. *Fix.* Fix `-Xmx` per dataset version now (e.g. 2g default; 8g for VOC2012 and Corel5K-R) with the rule N × Xmx ≤ 16 GiB, record the N actually used per dataset version in `PROJECTIONS.md` and the cost table (CPU time makes N a nuisance variable, not a validity condition), and state that no MPS TabPFN process runs concurrently with a timed C batch.

**m4. "CPU time does not depend on machine load" is not exact on 10 P + 4 E cores.** A process scheduled on an efficiency core accrues CPU seconds two to three times more slowly per unit of work. N = 8 fits the 10 performance cores only if nothing else CPU-bound runs; the Python drivers, Octave's own threads (unpinned unless `OMP_NUM_THREADS` reaches it), and the §1.9 MPS driver all compete. The 3× pilot margin in §6.6 probably absorbs an E-core episode, but the claim should be weakened and the condition stated. *Fix.* "N = 8 ≤ the 10 performance cores; during any timed pilot or run no other CPU-bound process (including §5, §6.9 and §1.9 drivers) runs on C; Octave is started with `OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1` as well; the load average is logged (already) and a timed run whose 1-minute load average exceeded 10 is re-timed." Replace "does not depend on machine load" with "is far less sensitive to machine load than wall clock".

**m5. §1.9 juxtaposes MPS repeated-CV verdicts with G single-run verdicts.** §6.1 says §1.9 "is never compared with a G result", but §1.9 "Reported" places the repeated-CV t, p, Δ "beside the canonical single-run values for the same contrast" and asks "whether the sign and the unadjusted p < 0.05 verdict agree" — those canonical values come from G. If §6.9 finds |ΔAP| > 1e-3 between devices, the agreement statement is confounded. *Fix.* Run the canonical 10-fold split on MPS as a sixth run of each §1.9 arm (one extra fold set, +20 % of a cheap analysis) and compare within device; or make the agreement sentence conditional on §6.9 passing at 1e-3.

**m6. Thread pinning and a recreated environment change the TabPFN/logreg runs relative to the stored results, and §6.9 cannot separate that from the device.** §6.9 compares G runs (pinned threads, new venv, new driver) with stored MPS results (unpinned, the August venv). `run_foundation_baselines.py` sets no thread environment today. If §6.9 shows a 1e-3 difference, nobody can say whether it is the GPU or the environment. *Fix.* Add **T03-g** to §6.8, run before §6.9: reproduce one stored result per harness **on the same device with the pinned settings** — `logreg_bagmean` on Scene in `.venv` (tolerance 1e-9 on all five metrics; lbfgs is deterministic) and `tabpfn_bagmean` on Letter Frost on MPS in the recreated `tabpfn_env` (tolerance 1e-3, as §6.9). A pass makes §6.9 attributable to the device; a fail is reported and the stored rows are labelled by environment.

Move the object clause back to the first sentence of the bullet.

### Notes (no action required)

- **N1.** On any row that passes the H4 gate, the Fieller set is bounded by construction: the gate "CI of Δ(multiview − bagmean) above 0" is exactly b̄ > t_{0.975,n−1}·√Var(b̄), which is the negation of the unbounded condition b̄² ≤ t²·Var(b̄) with the same t and variance. The unbounded clause is therefore dead text for s and c; harmless to keep, but the manuscript should not describe it as a possible outcome.
- **N2.** `power_table.py` Part D calls `wilcoxon(..., method="exact")` without `zero_method`; the default is `"wilcox"`, so it matches §1.6. Passing it explicitly would make the script self-documenting.
- **N3.** The upper-bound reading in H2-B is a directional argument (purged neighbours are near test rows and are removed wholesale; the control thins uniformly), not a theorem. The text already says "never leakage alone"; one more word, "heuristic", in the Interpretation bullet would forestall a reviewer who asks for a proof.
