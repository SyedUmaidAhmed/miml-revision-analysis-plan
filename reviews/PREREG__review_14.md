## Findings

**F1 (minor, material to self-containment): MIMLBagging's `<seed>` under the `rep-rK` labelling is not stated.**
DECISIONS row (11) says the five repetitions use "MIMLBagging's own `<seed>`, which is then fixed to 0–4"; row (13) changes only the *label* to `rep-r0..r4`. The plan attaches "with `<seed>` fixed to 0–4" only to the `seed-sK` branch (§1.3), which the plan itself says will not occur in practice, and the unconditional fallback sentence drops the clause ("KDIS exposes no seed, except MIMLBagging's own `<seed>`."). In the branch that will actually run, the text says only "its 5 repetitions are labelled uncontrolled (`rep-r0..r4`, `uncontrolled: true`), like the other methods'", which a reader can take as *same config, five runs*. The code does the row-(11) thing: `library_harness.py::kdis_block` rewrites the block to `<seed>k</seed>` in repetition k for MIMLBagging, and its own comment (lines 260–262) notes that "the five configurations are not nominally identical; the identity records it". The §1.5 sidecar sentence requires the seed to be recorded only for `seed-sK` units, so under `rep-rK` the plan does not require the varied seed to be stored either. The change table row (11) says "MIMLBagging `<seed>` 0–4" unconditionally, so the plan is internally mixed on the point.
*Fix (one clause in each of two places):* §1.3, after "like the other methods'": "its `<seed>` is still set to k in repetition k (DECISIONS row (11)); the label records that the seed did not control the run, not that the configuration was unchanged." §1.5 sidecar sentence: "…`uncontrolled: true`, and for MIMLBagging also the `<seed>` value used." No decision changes; this writes an already-decided clause into the branch that will execute.
